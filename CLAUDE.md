# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Working rules

- **Read `PLAN.MD` in full before any action.** It is the source of truth (French). Execute **one step (Étape) at a time**, in order. At the end of a step: check its acceptance criteria, tick the checklist (PLAN.MD §12), then **stop and wait for validation**.
- **Do not manage the git repository** (no init, commit, branch, push or GitHub repo creation): the maintainer handles it.
- **Never invent a number.** Every fiscal, budgetary or statistical value needs a source (official URL + access date) registered in `src/data/sources.json`. If unverifiable, set `"status": "A_VERIFIER"` and report it. Values not from a source are `"HYPOTHESE"`.
- No network calls at runtime; all data is bundled at build time.
- Code, comments and identifiers in English; UI text in French.
- Licences: code AGPL-3.0-or-later (`LICENSE`), data Licence Ouverte 2.0 (`LICENSE-DATA.md`). Every new source file starts with the two SPDX lines (`SPDX-FileCopyrightText: 2026 Mon budget pour la France contributors`, `SPDX-License-Identifier: AGPL-3.0-or-later`); `tests/licenseHeaders.test.ts` enforces it.
- Neutrality: symmetric slider bounds (from 0 to twice the current value wherever it makes sense), no party-labelled scenarios, no wording that judges a measure as good or bad.
- Accessibility: red/green never carry meaning alone. Always pair them with a +/− sign and an arrow icon. WCAG AA, full keyboard navigation.

## Project

Static citizen budget simulator ("Mon budget pour la France"), deployed to GitHub Pages. It shows the static, mechanical effect of tax and spending levers on (1) aggregates (revenue, spending, balance, debt in Md€ and % GDP, 5-year debt path) and (2) eleven single, childless household profiles (`student`, `apprentice`, `retiree1000`, `smic`, `employee1800`, `retiree2500`, `artisan`, `cadre3k`, `cadre10k`, `rentier5m`, `fortune100m`), plus the household described by the user ("Votre foyer"). No behavioural effects or macro feedback in v1.

Stack: Vite + strict TypeScript + Svelte 5, d3-hierarchy (treemap layout), Vitest, Zod. Plain CSS with variables, no heavy UI library. Repository layout: `src/engine/` (calculation), `src/ui/` (interface), `src/data/` (sourced data), `scripts/` (Node scripts run with type stripping, shared dataset loader in `scripts/lib/`), `config/` (build helpers), `tests/` (shared helpers in `tests/helpers.ts`).

## Architecture (see PLAN.MD §4–§8)

- `src/engine/`: pure calculation, **no UI dependencies**. `simulate(scenario)` returns aggregates, the debt path and per-profile results. `household/` holds one module per tax or benefit as pure `(profile, rules) => result` functions. Incidence assumptions (who bears VAT, employer contributions, corporate tax, property tax) are **data parameters, not hard-coded logic**.
- `src/data/*.json`: every numeric value uses the shape `{ value, unit, sourceId, asOf, status, note }`, validated by Zod. `scripts/validate-data.ts` (run in CI) fails on schema errors or unknown `sourceId` and reports the `A_VERIFIER`/`HYPOTHESE` counts.
- Reference data conventions: aggregates (`macro`, `revenues`) are national-accounts figures for `meta.accountsYear` (2025: INSEE semi-definitive account of Aug. 2026, Eurostat Oct. 2026 notification), `asOf` = year end. The COFOG breakdown is published a year later: `spending.json` keeps the latest published amounts (`structureYear`, 2024, Eurostat, VERIFIE) and `spending.scaling` (HYPOTHESE = total spending of the accounts year / of the structure year) brings them to the accounts year in `engine/cofog.ts` (`referenceGroupAmounts`); when INSEE publishes the 2025 breakdown (Dec. 2026), replace the amounts and set `structureYear` = 2025, `scaling` = 1. `macro.forecast` holds the government forecast for accountsYear + 1 (PLF 2027 / RESF / HCFP), shown in Methodology only; the apparent interest rate is the forecast one. Revenue items are on the gross basis (IR and IS before tax credits) and sum to `macro.totalRevenue`; `tests/data/consistency.test.ts` checks this and Σ scaled COFOG ≈ total spending (±0.5 %). Tax rules are the legislation in force in 2026 (`asOf` = date in force). Derived values carry the formula in `note`; modelling choices are `HYPOTHESE` even when computed from sourced inputs.
- Engine input: `resolveRules()` (`src/engine/rules.ts`) turns sourced data values into plain numbers and throws on any null value; `household/` functions take a `HouseholdInput` (annual euros) and those `Rules`. `householdLevies()` chains them. Tests replay sourced cases from `tests/fixtures/` (Urssaf mon-entreprise API, BOFiP / service-public / CAF worked examples); older examples are replayed with `rulesWith()` overrides.
- Profiles (`src/engine/profiles.ts`, `reference.ts`): gross salary is inverted from the target net; consumption = disposable income × (1 − savings rate) unless `annualAmount` is set; levies borne follow `taxRules.incidence` (`incidence.ts`, corporate tax grossed up at the statutory rate on dividends + retained earnings); in-kind services come from `inKindAllocation.json` rules applied to COFOG group amounts (`inKind.ts`). Project choices: education treated as a collective per-capita service (plus the per-student cost of COFOG 09.4 for the student); cash benefits not allocated except the prime d'activité, retirement pensions of the retiree profiles and the means-tested aids, each scaled by its level-3 spending item (`benefitItems.ts`), computed by `householdAids.ts` as for the custom household (housing aid stays a data value since profile rents are not described); health care per capita × age-group index (`inKindKeys`). Household modules also cover the apprentice (`salaryContributions(..., apprentice)`: employee levies only above 50 % of the SMIC; income tax exemption up to the annual SMIC; prime d'activité only above 78 % of the net SMIC), families (`incomeTax.ts`: `taxParts`, `quotientTax` with the quotient familial ceiling, couple décote, CEHR/CDHR couple thresholds; `benefits.ts`: household prime d'activité; `family.ts`: allocations familiales), pensions (`pension.ts`: CSG band by reference income, CASA, 1 % on the complementary part) and self-employed craftsmen (`selfEmployed.ts`, 2026 base reform).
- Simulation (`simulate.ts`): `createModel(dataset)` once, then `simulate(model, scenario)` (< 5 ms, tested). A scenario reaches the households through its rules and `ScenarioFactors` (profiles.ts: each benefit scaled by its level-3 items, `BENEFIT_ITEMS` in `benefitItems.ts`, each benefit on its own; property tax by its lever); a change of COFOG 01.7 (debt interest) changes the interest, not the primary balance. Shared numeric helpers (`sum`, `slice`, `cappedAllowance`, `invertIncreasing` for gross-from-net) are in `math.ts`. Levers (`levers.ts`) carry their reference value from data, symmetric bounds (0 to 2× the reference; rates capped at 100 %; a 0 % rate up to 1 point; the property tax change −100 % / +100 %; the barème indexation ±5 %), `revenueEffect` (static base × change, Md€) and `applyToRules` (household effect). Social contribution levers are the real rate of each contribution (base chosen by its ceiling: uncapped, 1, 4 or 8 PASS); energy excise levers are real tariffs per product (unit `tariff`; fuels stored in €/hl as in the published tariff tables and shown in €/L through `displayScale`, electricity and gas in €/MWh) whose household effect is weighted by `householdWeight`. Spending levers are amounts in Md€ (unit `billions`, reference = accounts amount, range 0 to 2×): a division amount scales its groups proportionally unless a group lever is set, and a group its level-3 items unless an item lever is set, the group then being the sum of its items (`spendingAmountsFor`). Level-3 items (PLAN.MD §13.2, Expert level, ids like `spending.cofog.10.7.rsa`) are listed under their group in `spending.json` (`items`, 2024 amounts scaled like the group, from the step 13 audit `docs/audit-v1.1/depenses.md`); the computed `other` item makes them add up exactly to the group (`referenceItems` in `cofog.ts`). Debt path (`macro.ts`): primary balance constant in % of GDP, interest = previous debt × apparent rate. New lever ids must be added to `tests/fixtures/lever-ids.json`; CDHR levers are deliberately absent (no sourced sensitivity).
- UI (`src/ui/`): `state/scenario.svelte.ts` (`ScenarioStore`, runes) holds only modified levers and derives `simulate()` on each change; `format.ts` holds French formatting and field parsing (comma decimal, clamping, extended bounds); components in `components/`. Aggregate deltas (`Delta.svelte`, `better`) are green when they improve the public accounts (revenue up, spending down, balance up, debt down) and red otherwise, with sign + arrow and the current value in small; profile cards show the scenario effect as two separate boxes, levies paid and benefits + services received (no net total), each coloured from 1 € (rounded). Small changes switch to M€ or € (`formatBillionsChange`). Treemap (`treemap.ts` + `components/Treemap.svelte`): d3-hierarchy layout drawn as absolutely positioned HTML buttons (keyboard/screen reader), diverging blue (up) / orange (down) / grey fill plus sign and arrow, coloured from 1 € of change; a click zooms into a division or calls `store.focusLever()`, which `LeverPanel` answers by opening, scrolling to and focusing the lever. Pages and sharing: `state/url.ts` routes the landing page (`pages/Home.svelte`, bare address; its figures come from the reference scenario, never hard-coded), `#/simulateur`, `#/methodologie`, `#/sources`, `#/a-propos`, `#/nouveautes` and keeps the simulator scenario in `#s=` + base64url(JSON), which always opens the simulator (`simulatorHash()` falls back to `#/simulateur`; replaceState, no history spam); `ScenarioActions` shares/exports/imports. The browser uses `bundledData.ts` (no Zod re-validation; CI validates) and lazily renders closed accordions (Lighthouse mobile ≥ 90). Spending layout below the functions (`spendingLayout.ts`, display preference in localStorage like the detail level, switch shown from the Detailed level): `tree` (default: rails, items opened by a button on their group) or `cards`, both in `SpendingList.svelte`; group sliders in `GroupLever.svelte`; `store.focusLever` opens the right accordion. Phones: levers in a bottom sheet, profile cards in a horizontal carousel. Themes: four designs chosen in the header (`ThemePicker`, `state/theme.ts`), `data-style` = `gazette` (default, listed first: newsprint, Fraunces + Inter) / `prestige` (black and gold, Cormorant + Inter) / `populaire` (bright and rounded, Nunito) / `neon` (data dashboard, Space Grotesk + JetBrains Mono), each in light and dark (`data-theme`); index.html applies the stored choice before the first paint. Components only use the CSS tokens of `app.css` (colours, fonts, radius, border width, tap size); `tests/ui/theme.test.ts` checks WCAG AA contrast of every palette. Fonts are bundled (@fontsource, OFL). Tests in `tests/ui/` (SSR render via `svelte/server`).
- Custom household (`engine/customHousehold.ts`, `simulateHousehold()` in `simulate.ts`, UI `HouseholdBuilder.svelte`, kept in localStorage only): contributions per adult, income tax per tax household (married/PACS = one, unmarried = one per adult with children attached to the first), family benefits for the whole household (each scaled by its spending item), in-kind services per member, consumption pattern of the reference profile with the closest standard of living (INSEE consumption units). Its result has the shape of a profile result, so `ProfileCard` renders it.
- Lever explanations (`src/data/explanations.json`, schema `explanationsFileSchema`): one entry per lever (summary, at most 7 sections with fixed headings, sourceIds); level-3 items described by their nature (`compensation`, `purchases`, `investment`, `subsidies`, `transfers`, `benefits`, `other`; `engine/natures.ts`) may use the `natures` template instead, `{groupe}` replaced by the group label (`ui/explanation.ts`), and their window links to the group's. Every text has the mandatory section « Ce que change une variation » (`VARIATION_HEADING`): two items, « À la hausse : … » then « À la baisse : … », of equal shape. `validateExplanations` (in `validate:data`) and `tests/data/explanations.test.ts` check coverage, registered sources, the variation section and no amounts in Md€ (the app shows them live). Spending texts follow the Eurostat COFOG manual (2019), nature texts the ESA 2010 definitions. `LeverInfo.svelte` (a `<dialog>`, opened by the lever's "?" through `store.openInfo`) lazy-loads the file, so it stays out of the main bundle. Texts are French, neutral and plain; a new lever needs its entry.
- Scenario report and impact texts (step 18): `engine/spendingAttribution.ts` gives each spending change to the lever that sets it (item lever, else group, else division; `spendingByLever`, with `spendingChanges` it adds up to the aggregates' spending change) and an order of magnitude in full-time posts (`positionsByLever`, `positionsByGroup`): compensation change × Σ sector share / (`spending.staffCosts` × scaling). Staff data: `staff` on COFOG groups (Eurostat D1 per sector, VERIFIE) and `staffCosts` (HYPOTHESE, RAP 2024 / INSEE / DREES); a group or division shows posts only when its D1 share ≥ `staffShareThreshold` (10 %), a compensation item always; benefit items show the change received per household instead; 03.2 uses `fireServices` (military firefighters of Paris and Marseille included, HYPOTHESE); 10.4, 10.5 have no staff data. UI: `impactText.ts` (upward/downward texts of equal shape, tested for every lever; posts rounded: none < 0.5, units < 20, else 2 significant figures), shown under each changed slider by `LeverControl`; `report.ts` + `ScenarioReport.svelte` (« Bilan » `<dialog>` opened from `ScenarioActions`, rendered only while open, focus back to its button).
- Profile impact is symmetric: `impact_total = (taxes_ref − taxes_scenario) + (in-kind services_scenario − services_ref)`. Spending cuts must reduce the services each profile receives (`inKind.ts`).
- **Lever IDs are stable** (hierarchical, e.g. `vat.standard`, `spending.cofog.07.1`). Never rename or reuse a lever ID; mark it `deprecated` instead. `tests/engine/lever-ids.test.ts` snapshots them.
- Scenario format: `{ schemaVersion, baseYear, levers: { id: absoluteValue } }`. It stores only modified levers, as **absolute values** rather than deltas. It is serialized to the URL hash (`#s=` + base64url), and `migrateScenario()` handles old schema versions.
- Changelog: `CHANGELOG.md` (French, Keep a Changelog; sections in order Ajouté, Modifié, Données, Méthode, Corrigé, Retiré; one line per change, continuation indented by two spaces, no Md€ amounts) is parsed at build time by `ui/changelog.ts` for the « Nouveautés » page (`pages/Changes.svelte`); the footer shows `package.json` version (`ui/version.ts`). Any user-visible change adds a line under the next version; a release bumps `package.json` (and `package-lock.json`), and `tests/ui/changelog.test.ts` fails unless that version is the first section. No GitHub releases or commit hash.
- Performance targets: `simulate` < 5 ms; a recompute on every slider `input` < 16 ms.

## Commands

- `npm run dev`: dev server. `npm run build`: production build into `dist/` (set `BASE_PATH=/<repo>/` for GitHub Pages).
- `npm test`: Vitest, runs `tests/**/*.test.ts`. `npm run test:coverage` enforces ≥ 90 % coverage on `src/engine/` (used in CI). Single file: `npx vitest run tests/resolveBase.test.ts`; single test: add `-t "<name>"`.
- `npm run lint` (ESLint + Prettier check, Markdown ignored), `npm run format`, `npm run typecheck` (svelte-check).
- `npm run validate:data`: Zod schemas + cross-file checks on `src/data/*.json` and status report; `node scripts/validate-data.ts --list` lists every non-VERIFIE value. Scripts run with Node's native type stripping (no tsx), hence `erasableSyntaxOnly` and explicit `.ts` import extensions.
- `npm run docs:profiles`: regenerates `docs/reference-profiles.md` (reference balance of the 11 profiles); a test fails when it is stale.
- `npm run openfisca:export` then `python scripts/openfisca-check/compare.py` (venv with `pip install -r scripts/openfisca-check/requirements.txt`, OpenFisca-France pinned): cross-check of the salaried and retired profiles and five family households with OpenFisca-France; writes `scripts/openfisca-check/out/report.md` (gitignored). Known, explained gaps are listed in `KNOWN_GAPS` of compare.py; `--strict` fails on unexplained gaps.
- CI (`.github/workflows/deploy.yml`) runs lint, typecheck, validate:data, test, build, then deploys `main` to Pages. `.github/workflows/openfisca-check.yml` runs the OpenFisca cross-check in a separate, non-blocking job and uploads the report as the `rapport-openfisca` artifact.
